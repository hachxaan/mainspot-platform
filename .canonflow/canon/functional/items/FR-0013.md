# FR-0013 — Recibo verificable de aceptación por la API, distinto del acuse humano

## Statement
La aceptación de un aviso por Telegram solo cuenta como `api_accepted` si la respuesta trae `ok: true`, `result.chat.id` igual al chat configurado, `result.message_id` entero positivo y `result.date` válido; se persiste la correlación `event_id ↔ message_id ↔ message_date` sin secretos. `api_accepted` nunca equivale a `human_acknowledged`. Una respuesta de otro chat, incompleta o perdida tras el envío no produce éxito: queda como `misrouted` o `api_acceptance_uncertain`, sin reenvío automático.

## Acceptance criteria
| id | given / when / then |
|---|---|
| AC-9131 | Given respuesta ok:true sin message_id, chat distinto o JSON inválido, when se envía, then el estado no es api_accepted ni se reporta delivery=ok. |
| AC-9132 | Given respuesta válida, when se envía, then el registro durable contiene event_id, message_id y message_date, y human_acknowledged sigue falso. |
| AC-9133 | Given el caso F-01 (api_accepted sin callback), when vence el plazo, then human_acknowledged es falso y el vencimiento queda registrado. |

Origen: hallazgo F-01 (SRC-0013) y mandato SRC-0011. DEC-0065 exige no registrar como éxito lo que falla y seguimiento; la forma concreta del recibo es PROPOSED hasta G-FUN.
