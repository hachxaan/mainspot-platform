# ARC-0001 — Arquitectura del AI Core: registro, despacho con versión fijada y adaptadores

## Statement
Módulo `src/ai/` dentro del monolito TypeScript/PostgreSQL existente; sin framework multiagente. Capas:

1. **Registro en BD** (DAT-0001): casos de uso, proveedores (con *referencia* a secreto), modelos por ID exacto con
   precio y fecha de origen, revisiones de prompt inmutables, revisiones de ruta (modelo + revisión de prompt +
   parámetros) con ciclo de vida, rollout por caso de uso (activa + canary %), suites y ejecuciones de evaluación.
2. **Despachador** (`AiDispatcher.invoke`): resuelve el rollout **en el momento de iniciar**, elige activa o canary
   por hash estable (`use_case_id`, clave de asignación) < porcentaje, y **fija** `route_id`/`prompt_revision_id` en la
   fila de invocación. Un job multi-paso guarda sus rutas fijadas al crearse; cambios de rollout posteriores no lo
   afectan. Orden: política de datos → presupuesto (reserva) → render del prompt → proveedor con deadline →
   validación de salida (1 reparación como máximo) → registro de uso/costo → resultado.
   Una ruta **DRAFT** nunca se ejecuta por simple pin: solo por una evaluación real autorizada existente o por un
   **grant de laboratorio** válido (DEC-0074, `src/ai/lab.ts`): `AI_ENVIRONMENT=lab`, grant vigente y no revocado,
   mismo tenant y usuario, emisor aún activo/autorizado, ruta dentro de la allowlist inmutable del grant y proveedor
   coherente. La comprobación se repite en el worker de jobs y antes de cualquier replay; un grant inválido o una
   selección ausente falla explícitamente (`lab_grant_invalid`), sin caer a otra ruta ni proveedor. La invocación
   registra `assignment=manual_lab`, `lab_grant_id` y `output_sha256`. La clasificación Jev recibe `labGrantId`
   solo como contexto (trazabilidad/revocación) y **siempre** resuelve su ruta normal TypeSafe; un grant nunca
   autoriza una ruta Jev DRAFT. Fuera de `lab` el laboratorio está deshabilitado: una petición con grant se
   rechaza (`lab_grant_invalid`), sin fallback ni cabecera ignorada.
3. **Render de prompt**: preámbulo de plataforma (no editable) + system + task con variables `{{nombre}}` de lista
   blanca y tipo declarado; el contenido no confiable va JSON-codificado dentro de delimitadores
   `<<<DATOS_NO_CONFIABLES ... >>>`. Variable desconocida o de tipo distinto ⇒ error antes de llamar.
4. **Adaptadores directos** (`src/ai/providers/`, DEC-0069/0073/0074): en DESARROLLO, `anthropic` (Messages API,
   esquemas estructurados y herramientas) para todo texto y razonamiento; `openai` solo imágenes (Images API,
   `gpt-image-2`); `typesafe` para Jev con el cliente existente; `simulated` solo para pruebas etiquetadas.
   Los modelos de texto OpenAI (`gpt-6-luna`, `gpt-6.1-sol`) quedan deshabilitados y sus rutas RETIRED; las rutas
   Anthropic históricas RETIRED de DEC-0073 no se reviven. Candidatas vigentes, sembradas por `ensureAiCatalog`
   como revisiones DRAFT nuevas con los prompts/parámetros existentes: `claude-sonnet-5-5` para diseño inicial,
   edición compleja y planificación de campañas; `claude-haiku-5-5` para las demás capacidades de texto; DRAFT
   hasta aceptación por suite PASS o revisión manual de laboratorio (FR-0019). Ambos adaptadores permanecen
   disponibles; un adaptador nunca cae a otro proveedor y no hay fallback automático.
   Costo `estimated` = uso × precio publicado guardado en el modelo. OpenRouter permanece deshabilitado; se
   preservan evidencia y costos históricos. Esta configuración de desarrollo no decide irreversiblemente el
   proveedor comercial de producción.
5. **Jev semántico** (`AiDispatcher.invokeClassification`, `src/engagement/ai-semantics.ts` y el intake
   existente): preguntas tipadas, presupuesto compartido DEC-0032 y política de datos DEC-0067.
6. **Herramientas del asistente**: funciones de lectura tipadas con tenant/actor de la sesión.
7. **Jobs durables** (`ai_job`): lease, reintento acotado, idempotencia por clave; worker integrado en el proceso
   del servidor (como el scheduler) o propio.

## Contrato de invocación
Entrada: `request_id`, `idempotency_key`, `tenant_id`, `actor_id`+rol, `origin`, `use_case_id`, entrada tipada
minimizada, `brand_facts_version`, `consent_ref`, `trace_id`, `deadline_ms`, `budget_usd` máximo y, opcionalmente,
`labGrantId` (solo el id opaco seleccionado por el usuario autenticado; no es permiso por sí mismo, se revalida).
Registro: `prompt_revision_id`+hash, `route_id`+versión, proveedor, modelo exacto, `policy_version`, estado,
validación, uso (tokens/imágenes), costo y su origen, latencia, error seguro, `assignment`
(`active`/`canary`/`pinned`/`eval`/`manual_lab`), `lab_grant_id` y `output_sha256`.
Salida: `schema_version`, resultado estructurado o referencias, `validation`, `uncertainty`, `usage`, `safety`.
El modelo nunca recibe credenciales, ids de tenant ni decide permisos.

## Notes / rationale
Configuración dinámica en BD con lectura del rollout por invocación (una consulta indexada): consistencia inmediata
entre procesos sin caché distribuida. Reutiliza aprobaciones, versionado web, scheduler y auditoría existentes.
